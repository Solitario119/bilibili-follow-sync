# 风控实测记录（risk control notes）

本文档记录开发过程中对B站"批量关注"风控机制的实测数据。这些参数直接决定了本项目的
默认限速策略，也是全网文档中鲜有明确记载的部分。**API与风控策略随时可能变化，本文
仅代表 2026年10月初 的观察。**

## 实测一：快速批量关注（2026-10-04）

- 场景：网页会话内直接调用 `api.bilibili.com/x/relation/modify`（`act=1`）
- 节奏：起步 0.5秒/个，连续成功后自适应提速至 0.35秒/个
- 结果：**前 298 个全部成功，第 ~299 个起几乎全部返回 `22015 风控拦截`**
- 冷却实验：静置 5 分钟、9 分钟后单发探测请求，仍返回 `22015`，未恢复

## 实测二：慢速批量关注（2026-10-05）

- 场景：同上，隔日进行
- 节奏：起步 3秒/个，连续成功后缓步提速至 2.2秒/个，遇拦截自动暂停 120 秒并放慢
- 结果：**再次在累计 ~299 个成功后被拦截**（当天第 1 个请求即成功，说明前一天
  的拦截已随日期切换恢复）
- 被拦截后即使暂停 120 秒、放慢到 4.6~8秒/个，后续请求仍全部失败

## 结论

| 事项 | 实测结论 |
| --- | --- |
| 每日配额 | 存在**约 300 次/天**的关注操作软配额（两天均在 299 卡住） |
| 配额恢复 | 随日期刷新恢复（隔日后第一次请求即正常），数分钟级冷却**无效** |
| 触发后表现 | 配额内连 1 秒间隔都没事；超配额后无论多慢都返回 `22015` |
| 读取类接口 | 拉取关注列表（`/x/relation/followings`）未观察到明显限制 |
| 已注销账号 | 返回 `22013 账号已注销`，无论何时都无法关注，应跳过 |

## 错误码速查（本工具视角）

| code | 含义 | 处理策略 |
| --- | --- | --- |
| 0 | 成功 | 计数成功 |
| 22013 | 账号已注销 | 永久失败，跳过 |
| 22015 | 风控拦截 | 疑似当日配额用尽，**立即停止**，次日续跑 |
| -412 / -352 | 请求被拦截 / 风控 | 同 `22015` 处理 |
| -101 | 未登录 | 提示重新登录 |
| -111 | csrf 校验失败 | 检查 `bili_jct` |

## 本项目的默认策略（据此制定）

1. 默认间隔 3 秒/个（最快不建议低于 1 秒，但提速并不能突破每日配额）
2. 内置每日尝试次数上限（默认 290），到顶自动停止
3. 连续 2 次风控拦截即自动停止，避免无效请求
4. 差集比对后逐个关注 → 天然幂等，任何时候中断，重新导入同一文件即可续跑

## 分组接口

关注分组保留功能用到以下端点。端点路径与参数已对照
bilibili-API-collect 原文档核对（**上游仓库已于 2026-01-28 收B站律师函后
关停删库**，核对依据为社区 fork 存档）；行为细节（分页、配额）仍待实测：

| 用途 | 端点 | 说明 |
| --- | --- | --- |
| 分组列表 | `GET /x/relation/tags` | tagid：0=默认分组、-10=特别关注；悄悄关注不在分组体系内 |
| 分组成员 | `GET /x/relation/tag?tagid=` | 分页 pn/ps；**data 直接是成员数组、无 total**，返回空页即到底 |
| 创建分组 | `POST /x/relation/tag/create` | 表单 `tag`（分组名，≤16字）+ `csrf`；22106=分组已存在 |
| 归组 | `POST /x/relation/tags/addUsers` | 表单 `fids`/`tagids`（逗号分隔）+ `csrf`；22105=未关注 |

两点保守处理：归组写入是否计入"约 300 次/天"配额未验证，工具把每次归组
也计入每日尝试计数；归组失败（含风控拦截）只告警不中断同步主循环，避免
影响关注进度。

## 扫码登录接口（桌面版使用）

| 用途 | 端点 | 说明 |
| --- | --- | --- |
| 生成二维码 | `GET /x/passport-login/web/qrcode/generate` | 返回 `qrcode_key` 与用于渲染二维码的 `url` |
| 轮询扫码状态 | `GET /x/passport-login/web/qrcode/poll?qrcode_key=` | `0`=成功（响应 Set-Cookie 写入 SESSDATA/bili_jct/DedeUserID）、`86101` 未扫码、`86090` 已扫码未确认、`86038` 失效需重新生成 |

登录态接口只读，与关注操作配额无关。核对依据同上（上游关停后的社区 fork 存档）。

## 取关接口

反向清理走同一个操作端点：`POST /x/relation/modify`，`act=2` 为取关
（`act=1` 为关注）。相关错误码：`22013` 账号已注销、`40061` 用户不存在
（两者视为跳过，关系保留）；`22015`/`-412`/`-352` 风控，同关注处理——
自动停止，次日续跑。

**取关是否计入"约 300 次/天"配额未实测**。工具按计入处理：取关与关注、
归组共用同一个每日尝试计数，超过上限自动停止。清理流程为删操作，入口
显式（面板④按钮 / CLI `--clean`），执行前完整预览名单并要求确认；默认
排除小号的特别关注（拉取 tagid=-10 成员），防止误删。
